# המעגל שעבר קומפילציה עובר את כל הבדיקות, ועדיין שגוי

*טיוטה. המספרים מהסבב הקשה של Veriq (Qiskit 2.6.1, qiskit-aer 0.18.2, mqt.qcec 3.11.0).*

## הפתיחה

בלוק של 5 קיוביטים עם שער אחד: `mcx([0,1,2], 3)`. מקמפלים אותו עם `transpile()` בהגדרות
ברירת המחדל ומריצים ב-Aer מ-|00000>. ההיסטוגרמה זהה למקור (TVD 0). גם כשמכניסים את
הקונטרולים לסופרפוזיציה, היא עדיין זהה. ואז מזינים |10100>: המעגל המקומפל הופך את קיוביט
המטרה, והמקורי לא נוגע בו.

לא חיפשתי את זה. זה צץ אצלי כהתראות שווא בכלי שלי.

## הבאג (שהוא בעצם מלכודת)

מאז Qiskit 1.3, ‏`transpile()` מניח כברירת מחדל `qubits_initially_zero=True`. תחת ההנחה הזאת,
‏`HighLevelSynthesis` רשאי לקחת קיוביטים פנויים ולהשתמש בהם כאנסילות "נקיות", כלומר
קיוביטים שמניחים שהם ב-|0>, כדי לפרק את ה-MCX בזול יותר (12 CX במקום 14 בדוגמה הזאת).

זו התנהגות מכוונת ומתועדת. ב-release notes של 1.3 כתוב במפורש שצריך להעביר `False`
כשמריצים את הטרנספיילר על תת-מעגלים של מעגל גדול יותר. מתחזק של Qiskit כתב את זה בפשטות
ב-issue ‏#13562: הקומפילציה בברירת המחדל מבטיחה תוצאות מדידה נכונות, אבל לא בהכרח שומרת
על האוניטרי.

אז זה לא באג של Qiskit. זו מלכודת שקטה. בכל פעם שמקמפלים בלוק ואחר כך משתמשים בו שוב
(`to_gate()`, ‏`compose`, ספרייה של אורקלים מקומפלים), אפשר לקבל בלוק שנכון רק אם קיוביט
"שהוא לא משתמש בו" במקרה נמצא ב-|0>. ואף אחד לא מזהיר.

שחזור מינימלי (קורה ב-1.3.0, ‏1.4.3, ‏2.0.0 ו-2.6.1, בכל רמות האופטימיזציה 0–3; ב-1.2.4 זה לא קורה):

```python
qc = QuantumCircuit(5); qc.mcx([0, 1, 2], 3)
t = transpile(qc, basis_gates=["cx", "rz", "sx", "x"])
Operator(t).equiv(Operator(qc))   # False
# התיקון: transpile(..., qubits_initially_zero=False)  -> True
```

התנאי: MCX עם 3 קונטרולים לפחות, ולפחות קיוביט אחד שאפשר "לשאול". בהדגמה שלי, תוכנית
גדולה מדליקה את q4 כדגל (|1>) ואז קוראת לבלוק המקומפל כ-`to_gate()` כשכל הקונטרולים
דולקים. התוצאה הנכונה היא |11111>. מתקבל |10111>.

## למה דגימה לא יכולה לתפוס את זה

הבלוק המקומפל נכון לכל קלט שבו q4 = 0. כל בדיקה שמתחילה מ-|0...0> משאירה את q4 = 0, ולכן כל
היסטוגרמה שתאספו תהיה זהה, לא משנה כמה shots. יותר shots לא יעזרו, כי הבדיקה שואלת את השאלה
הלא נכונה.

ראיתי את אותה תמונה במחקר המוטציות. הזרקתי 1036 מוטציות למעגלים מאומתים מהסבב הקשה,
ו-966 מהן באמת שינו את המעגל:

- היסטוגרמת Aer רגילה מ-|0...0> תפסה 327 מהן (**34%**).
- סריקה מלאה של כל קלטי הבסיס תפסה עוד 596.
- **43 (‏4.5%)** נתפסו רק בהוכחת שקילות פורמלית. 39 מהן הן מוטציות פאזה עם TVD 0 בכל קלט
  בסיס. ה-4 הנותרות הן π שנכתב כ-3.14: ‏TVD של בערך 1e-6, מול סף של 0.05 ב-4096 shots.

## איך Veriq תופס את זה

Veriq לא רק משווה דגימות. הוא מוכיח שהמעגל המקומפל שקול למקור כאוניטרי (QCEC, ואם צריך
גם מטריצה מלאה). על הבלוק הזה:

```
✔ PASS  Statistical test (Aer)   TVD=0.000
✘ FAIL  Reference equivalence    Counterexample: on input |10100> the outputs overlap only 0.0000.
=> VERDICT: FAIL
```

שתי התוצאות באות מאותו דוח: הדגימה ירוקה וההוכחה אדומה, עם קלט קונקרטי שאפשר להריץ שוב. כש-Veriq
מקמפל בלוק בעצמו, הוא עובד עכשיו עם `qubits_initially_zero=False`. הוא גם רושם הערת
`zero_init_hazard` בכל פעם שהקומפילציה בברירת המחדל הייתה שוברת את הבלוק.

גיליתי את זה בדרך הכנה. בסבב הקשה, 5 מתוך 28 מעגלים שכתבו מודלי שפה, והיו נכונים, קיבלו
FAIL מבדיקת הקומפילציה של Veriq עצמו, עד שמצאתי שהסיבה היא ברירת המחדל הזאת.

## קריאה לפעולה

- אם אתם מקמפלים חלקים ומרכיבים אותם אחר כך, העבירו `qubits_initially_zero=False`, או
  קמפלו רק את המעגל המלא בסוף.
- אם חבילת הבדיקות שלכם רק דוגמת מ-|0...0>, היא לא יכולה לראות את סוג הבאגים הזה.
- ההדגמה קצרה: `python examples/transpile_hazard/demo.py`, ורצה בערך שתי שניות. אשמח לשמוע
  אם זה משתחזר אצלכם, או אם יש לכם מקרים נוספים שבהם הדגימה אומרת PASS וההוכחה אומרת לא.
